🎯 Problem Statement & Target Personas

Blood banks operate under life-or-death constraints: whole blood expires after 42 days, incompatible transfusions can cause acute hemolytic reactions and death, and high-urgency trauma requests must supersede routine elective surgeries without starving prior routine orders. Manual spreadsheets and legacy hospital software lead to double-allocation race conditions, expired blood wastage, and non-compliance with donor recovery guidelines.

👨‍⚕️ Hospital Requesters

Trauma surgeons, ICU doctors, and hospital procurement staff who submit prioritized blood requests (Critical, Urgent, Routine) and track fulfillment status in real-time.

🩸 Voluntary Donors

Individuals who register, track donation history, and check their physiological eligibility under the strict 90-day whole blood donation recovery interval.

🛡️ Blood Bank Admins

Clinical administrators who monitor live inventory across 8 blood groups, inspect expiring units, and review the urgency-prioritized pending queue for transaction-safe approval.

📖 Executive Summary (Non-Technical)

Imagine an airport air traffic control system, but for blood bags. LifeFlow connects blood donors, emergency rooms, and blood bank managers on a single platform. It ensures that donors don't give blood too frequently (protecting their health), matches patient blood types with scientifically compatible bags, rushes blood to critical trauma patients before routine surgeries, and guarantees that two hospitals can never accidentally be promised the exact same bag of blood at the same time.

⚙️ Technical Summary (SDE Perspective)

LifeFlow is a modular Flask application built with a Layered Architecture separating presentation (Jinja2 + Vanilla JS), controllers (6 Blueprints), domain services (pure Python), and data access (SQLAlchemy ORM + MySQL 8.0 InnoDB). Data integrity is maintained using a 3NF schema with composite B-tree indexes, foreign-key cascades, and a UNIQUE unit constraint. Concurrency is handled via pessimistic row-locking (SELECT ... FOR UPDATE) inside atomic transactions, preventing double-allocation race conditions during high-concurrency request approvals.

🎯 2-Minute Technical Screen Pitch Architecture & Decisions

"In LifeFlow, my goal was to solve two hard engineering problems: real-time stock visibility and transactional consistency during concurrent allocation. I structured the system using a 3NF relational schema across 7 tables in MySQL 8.0. To prevent double-allocation under high concurrent load, the approval workflow uses pessimistic row-level locking (SELECT ... FOR UPDATE via SQLAlchemy's with_for_update()) inside an atomic transaction. Candidate units are selected using a First-Expired, First-Out (FEFO) strategy to minimize wastage of 42-day whole blood units, preferring exact blood matches before compatible alternatives. On the frontend, instead of adding WebSocket server state overhead, I implemented a lightweight 10-second polling engine in vanilla JavaScript that hits a composite-indexed aggregation query. I also enforced server-side donor eligibility: computing exact age (18+) and preventing donations within 90 days of a prior session with exact countdowns. The entire system is containerized in Docker Compose and verified by 28 Pytest tests, including a multi-threaded concurrency test."

🔬 5-Minute Onsite Deep-Dive Pitch Deep System & Trade-offs

"LifeFlow is designed around three architectural pillars: Layered Decoupling, Relational Rigor, and Concurrency Isolation. First, for decoupling: routes are strictly thin controllers across 6 blueprints. All business rules—like the 8x8 ABO/Rh transfusion matrix, donor eligibility, and FEFO inventory dispatching—reside in pure, framework-agnostic Python domain services. Second, for data modeling: the database is in 3rd Normal Form. Requesters and donors are decoupled 1:1 from the core users auth table. Physical blood units are tracked individually in blood_units, and when an allocation occurs, a join row is written into request_fulfillments. A critical schema detail is that request_fulfillments.unit_id is marked UNIQUE, creating a two-layer defense: even if application locking failed, MySQL will reject duplicate allocation at the storage engine layer. Third, query optimization: I introduced two composite B-tree indexes: blood_units(status, blood_type) which speeds up our 10-second polling count query from a table scan to an index range scan, and blood_requests(status, urgency, requested_at) which allows instant sorting of critical trauma requests ahead of older routine requests. When evaluating locking strategies, I chose pessimistic locking over optimistic concurrency control (OCC). In blood banks, stock is scarce; an OCC retry loop under high trauma load would repeatedly fail and waste critical seconds. Pessimistic locking guarantees deterministic serialization. I verified this by writing a multi-threaded Pytest test using Python's ThreadPoolExecutor racing two threads against a single AB- unit, proving that exactly one approval succeeds and zero negative inventory is possible."

🔄 2.B System Architecture & End-to-End Workflows

1. Application Startup & Request Lifecycle

When run.py executes, the application undergoes a strict sequential initialization:

  1. Environment Load: config.py loads .env via python-dotenv.
  2. App Factory: create_app() loads configuration and binds db.init_app(app).
  3. Context Processor: Registers inject_user() to provide current_user to all Jinja templates.
  4. Blueprint Mounting: Mounts 6 modular route blueprints (/auth, /donors, /requests, /inventory, /admin, /api).
  5. Table Verification: Executes db.create_all() within app context.
  6. WSGI Server: Starts Werkzeug HTTP server listening on configured port.

⚙️ 2.C Technologies, Dependencies & Trade-Offs

Direct vs. Transitive Dependencies

The project intentionally maintains a lean dependency manifest in requirements.txt:

  • Direct: Flask (HTTP micro-framework), Flask-SQLAlchemy (ORM), PyMySQL (DBAPI driver), python-dotenv (env loader), Werkzeug (WSGI utilities & PBKDF2 hashing), pytest (testing framework), cryptography (modern TLS/ciphers).
  • Transitive: SQLAlchemy (core relational engine), Jinja2 (templating), MarkupSafe (XSS string escaping), iniconfig / pluggy (pytest plugins).
  • Zero Bloat: No heavy external queue dependencies (Celery/RabbitMQ) or WebSocket servers were introduced for local development, keeping local setup frictionless and memory-efficient.

🤖 2.E AI/ML/LLM Component Verification & Safety Defense

Transparent Architecture Disclosure: Zero AI/ML Usage

A thorough scan of all manifests, dependencies (requirements.txt), and Python modules confirms that LifeFlow uses 0 AI/ML models, 0 LLM APIs, and 0 probabilistic neural networks. All blood compatibility matching, donor eligibility validation, and urgency queue sorting are implemented as 100% deterministic, pure algorithmic rule services.

💡 Interview Justification: Why Medical Software Must Reject Probabilistic LLMs

"If an interviewer asks whether we could use an LLM or neural network to predict blood compatibility, the answer is an emphatic NO. Transfusion medicine operates with zero tolerance for hallucinations: transfusing A+ red cells into an O- recipient causes acute fatal intravascular hemolysis. Deterministic dictionary lookups (O(1) in compatibility_service.py) provide mathematically provable safety, auditability, and compliance with healthcare regulatory standards (such as FDA 21 CFR Part 11)."

Q2 ARCHITECTURE Explain the Layered Architecture pattern used in LifeFlow.
▼
🎯 Direct Answer

LifeFlow separates concerns into 4 distinct layers: Presentation (Jinja2/JS), Controller (6 Blueprints), Domain Services (Pure Python business rules), and Data Access (SQLAlchemy ORM + MySQL 8).

📚 Foundational Concept

Separation of Concerns (SoC) ensures routing logic does not mix with medical validation or SQL queries, reducing cognitive load and making unit testing trivial.

🔍 Implementation Evidence

app/blueprints/api/routes.py (Controller), app/services/request_service.py (Service), app/models/inventory.py (Data Access)

⚖️ Technical Reasoning & Trade-offs

Keeping domain services free of Flask HTTP request contexts allows running business logic directly inside headless background workers or test scripts without mocking HTTP.

💥 Failure Scenarios & Edge Cases

Tight coupling of database queries inside Jinja templates or route controllers leads to spaghetti code, hidden N+1 queries, and untestable business logic.

🚀 Next-Level Production Improvement

Adopting Hexagonal Architecture (Ports and Adapters) with dependency injection interfaces to completely decouple the database driver from domain models.
